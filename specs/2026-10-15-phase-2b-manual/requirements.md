# Фаза 2b — manual: требования

Ветка: `feature/phase-2b-manual`. Пункт roadmap: `POST /api/v1/incidents` (ручной ввод) — тот же use case приёма, `eventId` генерирует сервер, метрики не выдумываются. Требования README: FR-01 (часть для ручного ввода), FR-03, FR-17 (маскировка ручного ввода).

## Цель

Дать человеку способ начать расследование без мониторинга: вставить текст ошибки или stack trace и получить инцидент с расследованием `QUEUED` — так же, как от автоматического события, через тот же use case и ту же маскировку.

## Объём

### Входит

1. **`POST /api/v1/incidents`** — тело по README §5.2 → `202 Accepted` + `Location` + `{incidentId, eventId, investigationStatus, deduplicated: false}`.
2. **Нормализация в `IncidentEvent`** (FR-01): ручной ввод становится тем же доменным событием, что и REST-событие.
3. **Метод use case `openManualIncident`**: маскировка → всегда новый инцидент + событие + расследование `QUEUED` + задание, без корреляции.

### Откладываем

| Что | Когда |
|---|---|
| `Idempotency-Key` для повторной отправки формы | P1 (README §5) |
| Извлечение класса исключения из `errorText` регулярными выражениями | не делаем: у ручного ввода нет корреляции, а LLM прочитает текст целиком (фаза 6) |
| Веб-форма ручного ввода | P1 (UI) |
| Добавление evidence к существующему инциденту | P1 (`POST /incidents/{id}/evidence`) |

## Ключевые решения

### Данные

| Решение | Почему |
|---|---|
| **Ручной ввод всегда создаёт новый инцидент**, даже если открыт инцидент с тем же fingerprint | README §5.2: «самостоятельный инцидент и фоновое расследование». По решению 2a коррелированное событие не создаёт расследования — ручной запрос молча остался бы без разбора (согласовано) |
| `eventId` = серверный UUID, `source` = `MANUAL`, `occurredAt` = время сервера (`Clock`) | README §5.1: при ручном вводе `eventId` задаёт сервер. Время из формы не спрашиваем: человек его обычно не знает |
| `type` — необязательный, по умолчанию `MANUAL`; `severity` — необязательная, по умолчанию `MEDIUM` | Вручную ошибку обычно описывают без классификации (согласовано) |
| Маппинг (согласовано): `title` → `summary`; `errorText` → `error.stackTrace` целиком, первая непустая строка `errorText` → `error.message`; `error.className` = `null`; `description` → `attributes.description`; `technology` → `technology` | Без расширения `IncidentEvent`: формат `payload` фазы 2a не меняется |
| «Метрики не выдумываются»: в событие попадает только то, что ввёл человек, плюс серверные `eventId`/`occurredAt`/`source` | README §5.2; FR-06 |
| Новое расследование и задание — как в 2a: `version = 1`, `QUEUED`, `INVESTIGATE`/`READY`, `dedupe_key = investigate:<investigationId>` | Один формат для worker'а фазы 3 |

### Use case и транзакции

- `IngestEventService.openManualIncident(IncidentEvent)`: `sanitizeManual` → тот же приватный путь «новый инцидент», что и в `ingest`, с уникальным `Fingerprint.forManual` (по итогам code review, см. «Отклонения»). Advisory lock и проверки идемпотентности не нужны: `eventId` уникален по построению, корреляции нет ни в одну сторону.
- Транзакция — новый `@Transactional`-метод в `TransactionalIngestion` (решение 2a: граница транзакции в адаптере).
- Новых портов и миграций нет.

### API

**`POST /api/v1/incidents`**

| Поле | Обязательно | Ограничения |
|---|---|---|
| `title`, `service`, `environment` | да | непустые, ≤ 200 символов |
| `errorText` | да | непустой; общий лимит тела 16 KB |
| `description` | нет | строка |
| `type` | нет | ≤ 200 символов; по умолчанию `MANUAL` |
| `severity` | нет | `LOW` \| `MEDIUM` \| `HIGH` \| `CRITICAL`; по умолчанию `MEDIUM` |
| `technology` | нет | объект |

Ответы: `202` + `Location: /api/v1/incidents/{id}` + тело того же формата, что у `POST /events` (`deduplicated` всегда `false`); `400` — невалидный JSON; `413` — тело > 16 KB; `422` — нарушены правила полей. Ошибки — `ProblemDetail` (общий `ApiExceptionHandler` фазы 2a).

## Граничные случаи

- Открыт инцидент с тем же fingerprint → всё равно новый инцидент со своим расследованием; старый инцидент не меняется (`updated_at`, событий не прибавилось).
- Одна и та же форма отправлена дважды → два инцидента (без `Idempotency-Key` это ожидаемо; P1).
- `errorText` из одних пробелов или переводов строк → `422`.
- `errorText` начинается с пустых строк → `error.message` = первая непустая строка.
- Секрет в `title`, `description` или `errorText` → в БД только `***`.
- Неизвестная `severity` → `422`.

## Допущения

- Лимит 16 KB достаточен для одного stack trace; если нет — его меняет настройка `copilot.ingestion.max-payload-size` из 2a.

## Лекции фазы

Новых навыков нет: транзакции, идемпотентность и маскировка разобраны в фазе 2a.

## Отклонения

1. **Общий ответ `IngestAcceptedResponse`** вынесен из `EventController` в отдельный класс (с фабрикой `202` + `Location`): оба эндпоинта отдают один формат. Небольшой рефакторинг кода 2a, поведение `POST /events` не изменилось (тесты 2a зелёные без правок).
2. **Тесты маппинга** — юнит-тесты `ManualIncidentRequestTest` на `toDomain(Clock)` с фиксированными часами, без Spring; по плану они и были «после кода», но вынесены из HTTP-тестов, чтобы проверять маппинг без БД.
3. **Code review (`/code-review high`, 7 находок):**
   - **исправлено:** изоляция работала только в одну сторону — ручной инцидент получал обычный fingerprint, и следующее авто-событие с тем же ключом привязывалось к нему (`findOpenIncident` берёт самый свежий). Теперь `Fingerprint.forManual` = SHA-256 от `manual|eventId`: ручной ввод не участвует в корреляции ни в одну сторону; Javadoc `openManualIncident` поправлен;
   - **исправлено:** `type`, `service`, `environment` в форме вводит человек — для ручного ввода они тоже маскируются (`EventSanitizer.sanitizeManual`); у авто-событий остаются идентификаторами;
   - **исправлено:** пустой `description` не сохраняется; `title` обрезается по краям; `error.message` ограничен 500 символами, полный текст — в `stackTrace` (маппинг из согласованного решения сохранён);
   - **опровергнуто тестом:** `service` из Unicode-пробела даёт 422, а не 500 (Hibernate Validator 9 отвергает его в `@NotBlank`), как и в 2a.
4. Остальное — по плану.
